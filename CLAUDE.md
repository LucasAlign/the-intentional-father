## Project

Steward — personal OS for the ADD entrepreneur: a daily dashboard with a scripture verse, marriage intention, top-3 task priorities, daily reflection journal, and an AI accountability chat partner. "Arlo" was the original internal name; the repo folder (`artifacts/arlo`) and package name (`@workspace/arlo`) keep it deliberately — see the Replit Environment Rules note below for why. ## Run & Operate

The dev servers below are already kept running by the Replit "Project" workflow — don't run them yourself; see **Replit Environment Rules**. Listed here for reference (what's running, on which port) and for non-Replit environments.

- `pnpm --filter @workspace/api-server run dev` — run the API server (port 8080)
- `pnpm --filter @workspace/arlo run dev` — run the Steward frontend (port 22384)
- `pnpm run typecheck` — full typecheck across all packages (builds `lib/*` project references first, then typechecks `artifacts/*` and `scripts`)
- `pnpm run build` — typecheck + build all packages
- `pnpm --filter @workspace/db run push` — push Drizzle schema changes to Postgres (dev only; `push-force` if it complains about data loss)
- `pnpm --filter @workspace/scripts run migrate-relationships` — one-time backfill moving relationships out of `profile.data` (pre-#28) into the `relationships` table; safe to re-run, skips users already migrated
- `pnpm --filter @workspace/scripts run migrate-pursuits` — one-time backfill turning each user's distinct `jobs.biz` values (pre-#29) into real `pursuits` rows and re-tagging their jobs; safe to re-run, skips jobs already tagged
- `pnpm --filter @workspace/scripts run migrate-commit-targets` — one-time backfill copying each commit's old single `relationshipId` (pre-#72) into the new `commit_relationship_targets` join table, which owns multi-person commitment targeting going forward; safe to re-run, skips already-migrated commits
- `pnpm --filter @workspace/api-spec run codegen` — regenerate the Zod schemas and react-query client from `lib/api-spec/openapi.yaml` (runs `typecheck:libs` afterward)
- Required env: `DATABASE_URL` (Postgres), `OPENAI_API_KEY` (Steward AI chat); optional `OPENAI_MODEL` (defaults to `gpt-5.4-mini`)
- Auth env: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`; optional `GOOGLE_ISSUER_URL` (defaults to `https://accounts.google.com`). Microsoft is a second OIDC provider: `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET`; optional `MICROSOFT_ISSUER_URL` (defaults to `https://login.microsoftonline.com/common/v2.0`)
- Email env: `RESEND_API_KEY` (approval and login-code emails via Resend); optional `RESEND_FROM_EMAIL` (defaults to `admin@lucasalign.com`). If unset: approval emails are skipped with a warning in every environment; login-code emails are skipped with a warning (code logged to console) in development, but `sendLoginCode` throws in production so `/login/email/start` fails loudly instead of returning a fake `{sent: true}`
- `PUBLIC_URL` (e.g. `https://1arlo.replit.app`): the canonical app origin. Takes priority over request headers (`x-forwarded-proto`/`x-forwarded-host`) everywhere an OAuth `redirect_uri` or an absolute link in an email is built (`lib/origin.ts`, `lib/email.ts`) — unset in a deployment, those fall back to proxy-forwarded headers, which can diverge from what's registered with the OAuth provider and cause `redirect_uri_mismatch`. Set it explicitly in any deployment that sits behind a proxy.
- `ADMIN_EMAILS` (comma-separated, case-insensitive): grants admin access (beta-invite approval, `routes/admin.ts`) and bypasses the beta-invite gate. Defaults to `witeyford@gmail.com` if unset. Read once at server startup (`lib/auth.ts`) — changing it in a running deployment's Secrets requires an actual redeploy/restart, not just a save, to take effect. Note the trailing **S** — a secret named `ADMIN_EMAIL` (singular) is silently ignored and the default applies instead.
- `LOG_LEVEL` (optional, defaults to `info`): pino log level (`lib/logger.ts`).
- `REMINDERS_CRON_SECRET` (optional): protects `POST /api/reminders/run` (#75's daily commitment-reminder digest, `routes/reminders.ts`). Unset means the endpoint always 503s — there's no persistent process on Replit's autoscale deployment to run this itself, so it has to be wired to an external scheduler (a Replit Scheduled Deployment, or any cron) that calls it once a day with `Authorization: Bearer <secret>`.
- `pnpm --filter @workspace/e2e run test` — run the Playwright usability-regression suite (#41) locally against whatever `arlo`/`api-server` you already have running (`reuseExistingServer` in `e2e/playwright.config.ts`); if neither is running, Playwright boots both itself. Needs `playwright install --with-deps chromium` once per machine first. Correctness beyond this suite's coverage is still verified via `typecheck` plus manual exercise of the running app — the suite is intentionally not comprehensive yet, see #41.

## Architecture

**API-spec-first codegen pipeline.** `lib/api-spec/openapi.yaml` is the hand-maintained source of truth for the HTTP API. `orval` (config in `lib/api-spec/orval.config.ts`) generates two downstream packages from it:
- `lib/api-zod/src/generated/` — Zod request/response schemas + TS types, imported by the server routes (e.g. `GetCurrentAuthUserResponse` in `routes/auth.ts`) for response typing/validation.
- `lib/api-client-react/src/generated/` — a react-query client (base URL `/api`), consumed by the frontend via a custom fetch mutator (`lib/api-client-react/src/custom-fetch.ts`).

Whenever the API surface changes, update `openapi.yaml` first, then run the `codegen` script — don't hand-edit files under either package's `generated/` directory.

**Request flow.** `artifacts/api-server/src/app.ts` wires: pino request logging → CORS → cookie/JSON parsing → `authMiddleware` (loads the user from the session cookie onto `req.user` for every request) → `/api` router. `routes/index.ts` mounts `health` and `auth` publicly, and gates `googleCalendar`, `steward`, `interview`, and `admin` routers behind `requireAuth` (401 if no session).

**Auth.** Four login paths, all converging on the same server-side session (session table + cookie, see `lib/auth.ts`) and the same `beta_invites` approval gate (a login only succeeds if the user's email has `status = 'active'`):
  - Google and Microsoft OIDC via `openid-client`, PKCE flow (`makeLoginHandler`/`makeCallbackHandler` in `routes/auth.ts`, keyed by `OidcProvider`). Google keeps the bare `/login`/`/callback` paths (its redirect URI is already registered); Microsoft uses `/login/microsoft`/`/callback/microsoft`. A successful Google login also stores a Google Calendar connection (`storeGoogleCalendarConnection`) when the calendar scope was granted. **#108 fix** — `authMiddleware.ts`'s `refreshIfExpired` used to `clearSession` (full logout) whenever the OIDC access-token refresh grant failed, tying an OIDC user's entire login lifetime to a ~1hr access-token refresh succeeding rather than the 90-day `SESSION_TTL` the session row and cookie both otherwise honor. This session-level `access_token`/`refresh_token`/`expires_at` triple is never actually consumed by anything (Google Calendar's own API calls go through a fully separate connection + refresh cycle in `routes/googleCalendar.ts`'s `googleCalendarConnections` table), so a failed refresh here now just leaves those fields stale on the session instead of ending it.
  - Email OTP (`/login/email/start`, `/login/email/verify`) — a 6-digit code hashed into `email_login_codes`, emailed via `lib/email.ts`/Resend; works for both first-time registration and returning sign-in.
  - Demo login (`/login/demo`) — creates a throwaway user and session with no OAuth round-trip and deliberately bypasses the beta-invite gate.
  - A mobile authorization-code exchange endpoint (`/mobile-auth/token-exchange`, `/mobile-auth/logout`) for a native client, Google-only.

All app data tables are scoped by `user_id` — this is a multi-user app, not single-user (despite older docs saying otherwise).

**Schema bootstrap, not migrations.** `artifacts/api-server/src/index.ts` runs idempotent `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` statements on boot to ensure auth/session tables exist. Day-to-day schema changes for app tables go through Drizzle (`lib/db/src/schema/steward.ts`, `auth.ts`) + `pnpm --filter @workspace/db run push`.

**Where things live:**
- `artifacts/arlo/src/pages/Home.tsx` — the entire app UI: a 6-tab mobile layout (Today / Tribe / Work / Sphere / Steward / Week — the nav tab id is still `"her"` internally, only the label changed, see #28), styled with inline `CSSProperties` maps (`R` root/nav, `S` screens, `M` modal) to preserve exact mockup fidelity — woodgrain + brass/parchment theme. `artifacts/arlo/src/index.css` holds the palette/font `:root` vars. `ModalSheet` (#36) is the one shared dialog shell every modal (~30+ call sites) renders through — dialog semantics, Escape-to-close, and on-close focus restore all live there once instead of per-modal. **#86 — modal scroll bouncing back, hiding Close/Cancel.** First attempt added `overscroll-behavior: contain` to `M.sheet` (the scrollable sheet itself) to stop a scroll gesture at the sheet's own top/bottom edge from chaining into the page behind the fixed `M.overlay` backdrop — this stopped the gesture from actually scrolling the page, but the bug persisted because iOS Safari's elastic rubber-band bounce is a property of the *body's own touch handling*, not of scroll chaining, so containment alone didn't touch it. Real fix: `ModalSheet`'s effect now calls a module-level `lockBodyScroll()`/`unlockBodyScroll()` pair that pins `document.body` via `position: fixed` (recording and restoring `scrollY`) for as long as 1+ modals are open, removing the body from that bounce physics entirely — reference-counted (not per-modal state) so a modal opening another modal on top can't have the inner one's unmount prematurely restore scroll while the outer one is still open. That fixed the page-behind bounce but not the whole bug: `M.sheet` itself still used `overscrollBehavior: "contain"`, which per spec only stops a scroll gesture from *chaining* to the page behind — it explicitly still permits the browser's own rubber-band bounce to render on the sheet's *own* top/bottom edges, which only shows up on a modal with enough content to actually reach an edge during a scroll (Tribe's Log a Commitment/Kept/Deleted lists, Sphere's History and walkthrough wizard) and not on shorter Work-tab forms that never scroll far enough to trigger it — read as "only some modals got fixed." Changed to `overscrollBehavior: "none"`, a strict superset of `"contain"` (still blocks chaining to the page behind, additionally suppresses the sheet's own local bounce too), so there's no tradeoff to it.

Today's own "Coming Up" card reads a separate no-range fetch of the same endpoint (server defaults to today when `start`/`end` are omitted), so it's naturally unaffected by the Calendar tab's toggles; its titles go through `briefTitle()` to stay short regardless of source (#98). `GET /coming-up` accepts an arbitrary `start`/`end` range with no server-side bound. **#115 — continuous-scroll Calendar tab.** `WeekView`'s nav-tab label stays "Week" (unchanged) but its own page heading is "Calendar", since it's no longer bounded to one week: `calendarRange()`/`calendarDays()` (Home.tsx) compute a fixed, generous window — originally 1 month back/6 forward matching this app's other bounded-window history views (Sphere's 12-week dashboard, 6-month history), widened to 1.5 years back and 1.5 years forward per direct user request after testing — rather than true infinite scroll — fetched once via `refreshWeek()` (shared by the mount effect and the tab's own sync button, so they can't drift) and rendered as one flat, always-mounted list of day rows the user scrolls natively; no fetch-on-scroll plumbing. The entire header — month bar (prev/next arrows, month label, sync, Today), page title/subtitle, and the two visibility-toggle chips — lives in one `position: sticky` block (`S.calendarHeader`) pinned to the top of the tab's own scroll container, not just the month bar alone, so none of it scrolls away with the day list. The month label itself is still tracked via a plain scroll-listener + `getBoundingClientRect()` comparison against day-row refs (`dayRefs`), the same imperative-DOM-measurement style `useBottomScrollFade` already uses elsewhere, not an Intersection Observer. The Today button lives in that same header row next to the arrows/sync button (not a separately floating button conditional on scroll position like its first cut) and always jumps to today's row. The sync button (`sync` `IconName`) re-runs `refreshWeek()` — every `GET /coming-up` call is already a live, uncached Google Calendar pull, so there's nothing separate to "force fresh" — and spins for a guaranteed minimum 1s (`Promise.all` with a `setTimeout`) via a `calendarSpin` CSS keyframe (declared alongside the pre-existing `micPulse` one in Home.tsx's root `<style>` tag) so the tap always reads as an action even when the refresh itself resolves near-instantly. `scrollToDay()` (arrows, Today, and the initial mount jump below) computes its own scroll offset manually — `target.getBoundingClientRect().top` minus the container's, plus `scrollTop`, minus the sticky header's own measured height (`headerRef`) — rather than `scrollIntoView({block:"start"})`, which would land the target row directly underneath the sticky header (still hidden) instead of just below it. A `useLayoutEffect` on mount calls `scrollToDay(todayKey, "auto")` so opening the tab lands scrolled to today immediately, before paint — previously it opened scrolled to the very top of the whole window, which visually read as "defaults to the wrong month" even though the header label itself was already correct. The arrows and Today button also call `scrollToDay(..., "auto")` (an earlier cut used the default `"smooth"`) — a `"smooth"` `scrollTo` fired again before the previous one finished animating is a known trigger for mobile Safari to stall the scroll container outright, which read as "the arrow only works a couple times, then needs a manual scroll to unstick"; an instant jump has no in-flight animation for a fast second tap to collide with. That fixed the stalling but not a second, asymmetric bug in the same area: the scroll-listener's own "which month is current" tracking (the `useEffect` above, unchanged) infers the month by scanning `months` in order and checking each one's row position against a pixel threshold, breaking on the first miss — and `scrollToDay` lands a jumped-to row's top at *exactly* that threshold, so a sub-pixel rounding difference between the listener's and `scrollToDay`'s independently-measured rects can flip the comparison either way. A miss on a *forward* jump leaves the listener's inferred month pinned on the old one (since the scan accumulates in order and bails at the first failure) — every next click re-targets the same month, reading as "the arrow only ever advances one month, no matter where you start." A miss on a *backward* jump is comparatively harmless (it just undershoots by one extra month, still net progress), which is why only forward paging ever got stuck this way, and why widening the window (`#115` above) surfaced it. Fix: `jumpMonth` and the Today button now call `setCurrentMonthKey` directly with the destination month's own key right after the jump, rather than waiting for the listener to re-derive it from scroll position — a deliberate jump already knows its destination with certainty, so there's nothing to infer. The listener itself is untouched and still the only source of truth while the user free-scrolls by hand. `calendarHeader`'s sticky block also bleeds a negative top margin (`-16px`, matching `S.scroll`'s own top padding) the same way its horizontal `-18px` margins already bled full-width, so its background hugs the very top of the scroll container instead of leaving a dead, unstuck gap above it. Its background/blur mirrors `R.navWrap` (the bottom nav bar) — this app's one other piece of persistent chrome sitting on top of scrolling content — rather than the warm walnut `glass` card gradient meant for content cards floating on the page; a first attempt used `glass` and read as inconsistent with the rest of the theme. `calendarHeaderLine`, an absolutely-positioned 1px brass gradient bar pinned to the header's own bottom edge, plays the same role `R.navLine` plays for the bottom nav — the actual visual separator between persistent chrome and the content scrolling underneath it, rather than a plain CSS border. **#128 — expandable commitment rows, edited in place.** A commitment row in a day's item list (`tag: "Commitment"`) is now expandable: tapping its own `▾`/`▴` toggle (`S.commitExpandBtn`) reveals who it's for (`commitTargetLabel`/`commitTargetSub`, the same helpers Tribe's own commitment rows use) and any notes, plus an Edit button — mirroring `SwipeCommitment`'s collapsed/expanded shape in Tribe (`Home.tsx`) rather than inventing a second look for the same data. Edit opens the same `CommitEditModal` Tribe already uses, directly from Week — no tab switch, no cross-tab "open this on landing" state, since `Home.tsx` already loads `commits`/`relationships` for the Tribe tab and simply passes them (plus `refreshCommits`/`refreshRelationships`) into `WeekView` as more props. `commitIdFromEventId()` reverses `/coming-up`'s synthetic negative id (`-(1_000_000 + the real commit id)`, #97) back to the real id so the full `Commit` object — untruncated text, notes, relationship targets — can be looked up instead of the truncated display-only projection `/coming-up` returns; the collapsed row itself now also shows that untruncated `commit.text` rather than the 80-char-sliced title. Saving or deleting from this modal refreshes both `commits` (so the expanded detail stays current) and Week's own `events` via the existing `onRefresh` (so a due-date change moves the row to the right day). Only commitment rows get this treatment — manual `coming_up` entries, Google Calendar events, and job due-date rows are unchanged, matching the issue's own scope.
- `artifacts/api-server/src/routes/interview.ts` — AI-driven onboarding interview, backed by `profile`/`interview_messages`. Two ways to revisit it later, both surfaced from the Profile menu (#92): **"Edit My Answers"** (`MyAnswersModal` in Home.tsx) is a direct form over the onboarding-derived `profile.data` fields (name, season of life, top priority, values, the four `planning_profile` fields, guardrails) — no AI involved, `PATCH /profile/answers` replaces whichever top-level keys are submitted, leaving the rest (including `voice`, which has its own Steward-tab toggle, and relationships/pursuits, shown here only as a read-only count linking to Tribe/Work) untouched. **"Redo the Interview"** reruns the exact same conversation flow (`POST /interview/restart` clears `interview_messages` for a clean slate, then the client visits `/interview?restart=1`, which tells `Interview.tsx` to skip its normal "already onboarded → bounce home" redirect for that one visit). ## Gotchas

- A composite TS project (like `lib/replit-auth-web`) that uses `import.meta.env` needs its own `src/env.d.ts` declaring `ImportMetaEnv`/`ImportMeta` — it has no Vite dependency, so `vite/client` types won't resolve. Skipping this breaks `typecheck:libs`, which `api-spec`'s `codegen` script runs at the end.
- `OPENAI_API_KEY` must be set (as a Replit secret in deployed envs) for AI chat/interview features to work.
- Journal and chat save on blur / form submit, not live.
- `lib/replit-auth-web`'s `useAuth()` retries its initial `GET /api/auth/user` check (up to 3 times, 1s/2s/4s backoff) before concluding the user is logged out. This exists because Replit's autoscale deployment has no persistent process (see `REMINDERS_CRON_SECRET` above) — after inactivity the instance spins down, so reopening the app can cold-start on this very first request. That endpoint always returns 200 with `{user: null}` for a genuinely logged-out visitor, so a thrown/non-ok response here is always an infra hiccup, never a real "not authenticated" — safe to retry generously. Without this, a single cold-start blip showed the full sign-in screen (`AuthGate`) even though the session cookie/row were still valid, which read as "got logged out" despite #108's fix (a separate, server-side bug) already being in place.
- The reminder scan (#75) computes "today" from the server's UTC clock — there's no per-user timezone anywhere in the schema. A commitment can land in the wrong day's bucket by up to ~a day for a user far from UTC; accepted tradeoff for v1, not a bug.
- Sphere's `weekStart` (#82) runs Sunday–Saturday (resets Saturday night at 11:59pm) and is client-computed using the browser's local Date methods — no per-user timezone field in the schema, it just relies on the client already being in the user's own timezone — and only validated, not recomputed, server-side; the same up-to-~a-day skew as the reminders gotcha above applies if the server ever falls back to its own UTC-based default (in practice the client always sends `week=` explicitly, so this is rarely hit).

## Replit Environment Rules

This project runs in Replit. The API server (`artifacts/api-server`, port 8080) and frontend (`artifacts/arlo`, port 22384) are managed by the Replit "Project" workflow (`.replit`'s `[workflows] runButton = "Project"`).

- **Never start or restart the server.** Don't run `pnpm --filter @workspace/api-server run dev`, `pnpm --filter @workspace/arlo run dev`, or any command that binds to port 8080 or 22384. The Replit workflow manages both — not Claude Code.
- **Edit files only.** Make code changes to files but don't try to run or serve the app. Replit handles hot-reloading for frontend changes automatically.
- **Don't use Docker or virtual environments.** Replit uses Nix.
- **Don't modify the root `package.json`, `artifacts/arlo/vite.config.ts`, or `lib/db/drizzle.config.ts`** unless intentional — these are managed by the Replit environment.
- **Don't rename the `artifacts/arlo` folder or the `@workspace/arlo` package name** without coordinating with a human first. Replit's own "Project" workflow almost certainly invokes `pnpm --filter @workspace/arlo run dev` by that exact package name (per the command listed at the top of this section) — that workflow config lives in Replit's project settings, not in this repo, so an agent can't see or update it. Renaming either would silently break the dev server on the next Replit restart with no way to verify or fix it from here. This is why #6 (the Arlo→Steward rename) deliberately renamed identifiers, components, and internal file names but left the folder and package name alone.
